# 06 · 护城河:AI Deployment Intelligence

## 护城河不是什么

- ❌ 不是 Ollama —— 任何人都能封装一个安装器
- ❌ 不是某一个开源模型 —— 模型每几个月就换代,谁都能下载
- ❌ 不是 UI —— 界面可以被抄

## 护城河是什么

真正需要积累的是一个持续进化的映射:

```
什么用户 + 什么任务 + 什么数据 + 什么预算 + 什么硬件
                        ↓
        = 什么模型和部署方案效果最好
```

我们称之为 **AI Deployment Intelligence**。

## 数据从哪里来

平台的每一次使用都在产生别人拿不到的数据:

| 环节 | 产生的数据 |
|------|------------|
| 需求选择 | 真实用户想用 AI 做什么(需求分布) |
| 设备检测 | 真实用户手里有什么硬件(硬件分布) |
| 自动安装 | 什么组合能装成功、什么组合会失败(兼容性地图) |
| RAG 使用 | 什么切片/Embedding 方案对什么文档效果好 |
| Teach My AI | 什么任务上模型答错了什么(能力边界实测) |
| 微调 | 什么数据量 + 什么方法带来多少提升 |

## 飞轮

```
更多用户 → 更多部署数据 → 推荐方案更准 → 安装成功率更高、效果更好
   ↑                                                      ↓
   ←←←←←←←←←←← 口碑与转化更好 ←←←←←←←←←←←←←←←←←←←←←←←←←←←
```

新模型发布时,竞争对手只能看 benchmark 猜;我们有几万次真实部署的实测数据,知道它在 8GB 显存的英文合同问答场景里到底行不行。

## 对产品的要求

从 MVP 第一天起就要埋点(匿名、可关闭):

1. 每次推荐方案的输入(需求/硬件)和输出(方案)
2. 安装结果:成功/失败/失败原因
3. 使用质量信号:用户纠正、点赞点踩、会话时长
4. 方案变更:用户从推荐方案换到了什么

**这些数据结构的设计优先级,等同于产品功能本身。**
