# 13 · 测试、实验与假设验证

> 本文回答三个问题:**怎么做测试、怎么做实验、怎么验证假设。**
> 面向 Build My AI 团队(工程 / 产品 / 增长),给的是可以今天就照着跑的流程、清单、指标目标和可复制模板。
> 所有数字都标注为 **目标 / 假设(target)**,不是既成事实——它们本身就是要被实验证伪或证实的东西。

产品前提(贯穿全文):
- **产品**:面向非技术用户的个人 AI 一键搭建平台。流程:需求 → 检测硬件 → AI 顾问推荐开源模型 → 一键本地安装包 / 云端手册 → 拖入文档做 RAG → 带来源引用的对话 → Teach My AI 反馈微调。
- **MVP**:Windows + NVIDIA,美国市场,本地优先(数据不出设备)。
- **North Star Metric(北极星)**:**Weekly Answered Users** —— 每周从自己的私有 AI 得到「有用且带来源」回答的活跃用户数。
- **激活定义(Activation)**:新用户 **30 分钟内**拖入 **≥1 个文档**,并得到**一个带来源引用的正确回答**。
- **护城河**:AI Deployment Intelligence —— 「什么硬件 + 什么任务 = 什么方案最好」的映射。测试与埋点的最终目的之一,就是持续喂养它。

## 1. 测试分层总览

我们把「测试」拆成三层。三层解决的问题完全不同,不能互相替代:代码测试保证**软件不崩、不被注入**;部署测试保证**在真实硬件上装得上**;用户测试保证**普通人真的能独立跑通并觉得有用**。

| 层 | 名称 | 回答的问题 | 现状 | 主要产出 |
|----|------|-----------|------|---------|
| ① | 代码 / 软件测试 | 代码正确吗?安全吗?改动会回归吗? | 已有 `frontend/tests`(静态扫描 + `esc()` 单元测试 + 无头浏览器 XSS) | 绿灯 / 红灯,退出码,可进 CI |
| ② | 部署测试 | 在真实硬件上装得上、跑得动吗? | 待建:硬件矩阵 | 安装成功率矩阵 + 失败原因分布 |
| ③ | 用户 / 可用性测试 | 非技术用户能独立跑通吗?觉得有用吗? | 待建:可用性测试 + Beta | 完成率、SUS、卡点清单 |

### 1.1 第 ① 层:代码 / 软件测试

**已有基础(不要重复造):** `bash frontend/tests/run.sh`

- `security.test.js`:静态扫描 + `esc()` 单元测试 + 数据流与网络边界断言(89 项),零依赖,只需 Node。网络边界:全站仅 `assets/local-llm.js`(聊天页的可选本机模型连接器,见 [16 本地 AI 接入网页](16-local-ai-web-integration.md))允许发起请求,且只能指向 `127.0.0.1` 的本机服务;其余文件出现任何网络 API 即测试失败。
- `xss.browser.html`:无头浏览器里向真实 `chat.js` 投喂 XSS payload,验证被当纯文本渲染。
- `run.sh`:串起两者,任一失败退出码 `1`(可直接进 CI / pre-commit)。

**建议补充的测试类型**(随着 MVP 从演示站——目前除聊天页可选接入本机模型外均为静态演示——走向真实安装器,逐步补齐):

| 类型 | 测什么 | 建议工具 | 触发时机 |
|------|--------|---------|---------|
| 单元测试(unit) | `esc()`、硬件档位判定函数、推荐引擎打分函数、RAG 切片函数 | Node 内置 `assert` / Vitest | 每次改动 |
| 集成测试(integration) | 「设备检测 → 推荐方案」链路、「文档 → 切片 → Embedding → 检索」链路 | Vitest + 本地假数据 | 每次 PR |
| 端到端(E2E) | 引导向导五步全流程能生成正确安装包 / 云端手册;聊天页能出带来源回答 | Playwright(无头) | 每晚 nightly + 里程碑 |
| 合约测试(contract) | 本地 API 的 OpenAI 兼容格式(请求 / 响应结构) | schema 断言 | API 改动时 |

> **原则**:能用现有零依赖脚本覆盖的,就别引重框架;`frontend/tests` 的「小依赖面」是资产,别轻易破坏。

### 1.2 第 ② 层:部署测试(安装成功率硬件矩阵)

这是我们**最独特、也最容易被忽略**的测试。竞品可以抄 UI,抄不了「哪种硬件 + 哪种模型 = 装得上」的实测地图——这正是护城河数据的来源(见 [docs/06-moat.md](06-moat.md))。

**硬件矩阵(VRAM 档位 × 系统)。目标:每格安装成功率 ≥ 90%(无人工干预)。**

| VRAM \ 系统 | Windows 10 | Windows 11 |
|-------------|-----------|-----------|
| 6 GB | 成功率 ≥90% | 成功率 ≥90% |
| 8 GB | 成功率 ≥90% | 成功率 ≥90% |
| 12 GB | 成功率 ≥90% | 成功率 ≥90% |
| 16 GB | 成功率 ≥90% | 成功率 ≥90% |
| 24 GB | 成功率 ≥90% | 成功率 ≥90% |

**每格记录:**

| 字段 | 说明 |
|------|------|
| 显卡型号 / 驱动版本 | 如 RTX 3060 / 546.xx |
| 推荐方案 | 引擎推荐的模型 + 量化 + 推理后端 |
| 安装结果 | 成功 / 失败 |
| 失败原因码 | 见 §6 失败原因码表 |
| 端到端耗时 | 下载 → 第一次成功问答的分钟数(目标 ≤30 min) |
| 首答质量 | 带来源且正确 / 带来源但错 / 无来源 |

**执行方式(不必一开始就买齐显卡):**
1. 团队自有机器先覆盖能覆盖的档位。
2. 用云 GPU 实例(不同 VRAM 型号)跑「云端手册」路径的可复现验证。
3. Beta 用户上报真实机型,自动补全矩阵(埋点 §6)。
4. 每个里程碑在矩阵上**回归一遍**(见 §9)。

### 1.3 第 ③ 层:用户 / 可用性测试

分两种:
- **可用性测试(usability test)**:实验室式,5–8 人,深度观察,找**卡点与措辞问题**(§3)。
- **Beta 测试**:真实环境,10–20 人,持续几周,验证**端到端成功率与留存**(§4)。

## 2. 最该先验证的高风险假设清单(Riskiest Assumptions)

创业不是把功能做完,而是**按风险从高到低,一条条把假设杀掉或验证**。下面按「如果错了,产品就不成立」的杀伤力排序。每条给:**假设 → 如何证伪 → 通过标准**。

| # | 风险假设 | 如何证伪(最省钱的实验) | 通过标准(target) |
|---|---------|------------------------|------------------|
| A1 | 非技术用户能在 30 min 内、无终端、无术语地跑出可用本地 AI | 5–8 人可用性测试 + Beta 实测,记录端到端时间与卡点 | ≥70% 首次可用性测试用户独立完成;Beta ≥90% 安装成功 |
| A2 | 安装在真实硬件上足够稳(不会一半人装失败) | 硬件矩阵回归 + Beta 真机上报 | 每档 VRAM 安装成功率 ≥90% |
| A3 | 推荐引擎选的模型「够聪明」——用户觉得答案有用 | 激活率 + 点赞率 + Teach My AI 纠正频率 | 激活用户里 ≥60% 首答被判「有用」 |
| A4 | 带来源引用的 RAG 回答比「裸 LLM」更被信任、是核心价值 | A/B:有来源 vs 无来源两版回答,看信任度与留存 | 有来源版留存 / 满意度显著更高 |
| A5 | 非技术用户真的在意「数据不出设备」,愿为此选本地 | 落地页信息架构 A/B;访谈中该卖点的自发提及率 | 「本地 / 隐私」进入用户自述前三理由 |
| A6 | 有人愿意为此付费(Pro $29 / Business $299) | 定价页 + 假门(fake door)升级点击 → 意向调研 | Beta 结束时 ≥15% 活跃用户表达明确付费意向 |
| A7 | 免费匿名数据能真正喂养护城河(数据够用、够干净) | 检查埋点数据能否重建「硬件+任务→最佳方案」映射 | 能从数据得出至少 1 条此前不知道的部署建议 |
| A8 | 获取成本可控(非技术用户找得到、看得懂落地页) | 落地页转化实验 + 渠道测试 | 落地页 → 注册 / 下载转化 ≥ 目标(见 §5) |
| A9 | 云端手册路径对「硬件不够」的用户是可行出路 | 云端手册可用性测试 | 云端路径也能达激活定义 |

**用法**:每周实验会议(§8)从这张表**从上往下**挑当前最该打的一条,设计实验去证伪它。**一次聚焦一条高风险假设**,不要平摊精力。

## 3. 如何跑一次可用性测试(Usability Test)

目标:在**真人身上**发现「哪一步卡住了、哪个词看不懂」。5–8 个非技术用户就能暴露约 80% 的严重可用性问题——**不需要大样本**。

### 3.1 招募

- **人数**:5–8 人。宁可分两轮(先 5 人 → 修 → 再 3 人)。
- **画像**:美国市场、非技术、Windows + NVIDIA、有真实文档需求(合同 / 报告 / 笔记 / 客服 FAQ)。**排除**开发者、AI 从业者。
- **渠道**:朋友的非技术亲友、本地小企业主、Reddit 非技术社群、UserTesting / Respondent(付费招募)。
- **报酬**:$40–75 / 45 分钟,建议给。

**招募话术模板(可直接复制):**

```
主题:帮我们测个新产品,45 分钟,报酬 $50

你好 ___,

我们在做一个让「完全不懂 AI 的人」也能在自己电脑上装一个私人 AI 助手的工具
(你的文档不会上传到任何云)。想请你花 45 分钟试用一下,边用边说出你的想法——
你不需要懂任何技术,恰恰是「不懂」才最有价值。

- 时间:45 分钟,线上视频 + 屏幕共享
- 报酬:$50 礼品卡
- 你只需要:一台 Windows 电脑(带 NVIDIA 显卡)和一份你平时会用到的文档

方便的话回我三个你有空的时间段就行,谢谢!
```

### 3.2 主持人脚本(Moderator Script,逐字可念)

```
【开场 · 3 分钟】
谢谢你来。今天大约 45 分钟。先说三件事:
1) 我们测的是「产品」,不是「你」——任何卡住都是产品的问题,对我们最有用。
2) 请「出声思考」:看到什么、想点什么、期待会发生什么,都请说出来。
3) 我不会在中途帮你——因为真实用户装的时候身边也没有我。你尽管试。
可以录屏吗?只用于内部改进,不外传。

【背景 · 3 分钟】
- 你平时电脑上会处理哪类文档?
- 你用过 ChatGPT 之类的工具吗?最担心它什么?(听「隐私 / 数据」是否自发出现)

【任务 · 30 分钟】
我给你一个网页 / 安装包。请你把它当成自己在家里第一次用。开始吧,记得出声。
(不引导、不解释术语。只在完全卡死 >2 分钟时问:「你现在期待点哪里?」)

【收尾访谈 · 6 分钟】
- 整个过程,最困惑的一步是哪一步?
- 有没有哪个词你不确定是什么意思?
- 你会不会把它推荐给朋友?为什么?
- 如果只能改一件事,你希望改什么?
- (最后做 SUS 量表)
谢谢!这对我们帮助巨大。
```

### 3.3 任务卡(Task Cards,发给用户)

| 卡号 | 任务(给用户看的原话) | 成功判据(观察者用) |
|------|----------------------|--------------------|
| T1 | 「假设你想让电脑帮你读你的文档并回答问题。请从这个页面开始,直到你的 AI 装好。」 | 走到安装完成 / 云端手册就绪,无需主持人帮助 |
| T2 | 「把你带来的那份文档交给你的 AI。」 | 成功拖入 ≥1 文档并完成索引 |
| T3 | 「问它一个只有看了这份文档才能答对的问题。」 | 得到**带来源引用**且正确的回答 |
| T4 | 「如果它答得不好,想办法告诉它。」 | 找到并使用 Teach My AI 反馈 |
| T5 | 「你觉得这个要花钱吗?找一下价格。」 | 能找到定价信息,理解 Free / Pro / Business |

### 3.4 观察记录表(每个用户一份)

| 字段 | 记录内容 |
|------|---------|
| 用户编号 / 画像 | U01 / 45岁 小企业主 / RTX 3060 / Win11 |
| T1 起止时间、是否独立完成 | 例:0:00–8:20,是 |
| 卡点(时间戳 + 一句话) | 例:3:12 不懂「量化 Q4」是什么 |
| 看不懂的词 | 例:VRAM、Embedding、量化 |
| 情绪信号 | 皱眉 / 叹气 / 说「这个我不确定」 |
| 求助意图(想问却没人) | 例:「这里是不是该点这个?」 |
| 是否达激活定义(30min / 1文档 / 带来源正确答) | 是 / 否 + 实际耗时 |
| 用户原话金句 | 直接引用,别改写 |

### 3.5 SUS 量表(System Usability Scale,10 题,标准)

用户对每题打 1(强烈不同意)–5(强烈同意):

```
1. 我愿意经常使用这个产品。
2. 我觉得这个产品过于复杂。
3. 我觉得这个产品很容易上手。
4. 我需要技术人员帮忙才能用起来。
5. 我觉得它的各项功能整合得不错。
6. 我觉得它前后不一致 / 别扭的地方太多。
7. 我想大多数人都能很快学会用它。
8. 我觉得用起来很别扭 / 笨重。
9. 我用的时候很有信心。
10. 我得先学很多东西才能开始用。
```

**计分**:奇数题得分 =(答案 − 1);偶数题得分 =(5 − 答案);两者相加 × 2.5 = 0–100 的 SUS 分。

| SUS 分 | 解读 | 目标 |
|--------|------|------|
| ≥80 | 优秀 | 长期目标 |
| 68 | 行业平均 | **MVP 阶段过线目标 ≥70(target)** |
| <68 | 低于平均,须改 | 触发重设计 |

### 3.6 结果如何转化为行动
- 把所有卡点按「出现人数 × 严重度」排序 → 生成待办。
- **≥2 人卡在同一步 = 必修**。
- 「看不懂的词」清单直接反哺文案(呼应 Beta 的「零术语」目标)。

## 4. Beta 测试计划(10–20 个真实用户)

可用性测试在「实验室」,Beta 在「真实的家里和办公室」。目标:验证**端到端成功率、激活、留存**,并第一次真正喂养护城河数据。

### 4.1 目标与成功标准

| 维度 | 成功标准(target) |
|------|-------------------|
| 端到端 | 用户 **30 分钟内**拥有可用的本地 AI(达激活定义) |
| 安装成功率 | 支持硬件上 **≥90%** |
| 术语 | **零术语**——用户全程无需理解任何 AI 名词 |
| 激活率 | 完成注册 / 下载的用户中 **≥50%** 达激活定义 |
| 一周留存 | **≥40%** 的激活用户第 2 周仍产生 ≥1 次带来源问答 |
| 定性 | ≥10 条可用的用户金句 / 卡点,可指导下一里程碑 |

> Beta 期间**全免费**;Pro / Business 需注册。Free 免注册、收匿名数据。

### 4.2 招募

- **人数**:10–20。
- **渠道**:可用性测试留存的人、Reddit(r/LocalLLaMA 边缘的非技术用户、r/smallbusiness)、印刷 / 会计 / 律师等「有文档、怕上云」的小行业社群、朋友圈非技术人群、等待列表(落地页留邮箱)。
- **硬件门槛**:Windows 10/11 + NVIDIA(覆盖 6–24GB 各档,尽量凑齐矩阵)。

### 4.3 上手包(Onboarding Kit,发给每个 Beta 用户)

```
欢迎加入 Build My AI Beta 🎉

你会得到:一个属于你自己的 AI,跑在你自己的电脑上,你的文档不会离开这台机器。

三步开始:
1) 打开这个链接 → 点「开始」。它会自动看你的电脑配置,给你推荐方案。
2) 按提示一键安装(全程不需要打开任何黑色命令行窗口)。
3) 把一份你自己的文档拖进去,然后开始提问。

我们只想请你做一件事:
👉 每次用完,如果方便,点一下答案下面的 👍 / 👎。这是它变聪明的方式。

遇到任何卡住:
- 截个图发到这个群 / 邮箱 ___,越具体越好(卡在哪一步、看到什么)。
- 记住:卡住是「我们的 bug」,不是你的错。

隐私:我们默认只收集匿名的使用数据(比如「安装第几步失败」),
永远不会收集你文档里的任何内容,而且你随时可以在设置里关掉。
```

### 4.4 指标回收节奏

**每日(自动埋点 + 群里巡查):**

| 指标 | 来源 |
|------|------|
| 新安装数 / 成功数 / 失败数 + 失败原因码 | 埋点 §6 |
| 新增达激活定义人数 | 埋点 |
| 硬件矩阵新覆盖的格子 | 埋点(设备档位) |
| 群里报障(截图) | 人工 |

**每周(周会前汇总,进 §8 实验看板):**

| 指标 | 公式 / 定义 | target |
|------|-----------|--------|
| 安装成功率 | 成功 / 总尝试 | ≥90% |
| 激活率 | 激活人数 / 下载人数 | ≥50% |
| 中位端到端时间 | 下载→首个带来源正确答 的中位分钟数 | ≤30 min |
| Weekly Answered Users | 本周得到 ≥1 带来源有用回答的人数(北极星) | 周环比增长 |
| 一周留存 | 上周激活用户本周仍活跃 / 上周激活 | ≥40% |
| 点赞率 | 👍 /(👍+👎) | ≥70% |

### 4.5 Beta 退出标准(达到即可扩大规模)
- 安装成功率 ≥90% 且失败原因收敛到 ≤3 类可解释原因。
- 激活率 ≥50%,中位端到端 ≤30 min。
- 至少 1 条护城河洞见(某硬件+任务的最佳方案被数据验证)。
- SUS ≥70。

## 5. 指标体系:North Star + AARRR

### 5.1 North Star Metric

> **Weekly Answered Users** = 每周从自己的私有 AI 得到 ≥1 个「有用(带来源)」回答的活跃用户数。

- **为什么是它**:同时抓住「装成功了」+「真的在用」+「答案有用」+「体现了带来源这一核心差异化」。纯下载数、纯 DAU 都会骗人。
- **拆解**:`Weekly Answered Users = 激活用户数 × 周活跃比例 × 有用回答命中率`。三个乘子分别对应「装得上」「愿意回来」「答得好」,任何一个塌了北极星都涨不动。

### 5.2 AARRR 海盗指标漏斗

**所有目标数值均为 Beta 阶段的目标假设(target),用来被实验校准,而非承诺。**

| 阶段 | 指标 | 定义 / 公式 | Beta 目标(target) |
|------|------|------------|-------------------|
| **Acquisition 获取** | 落地页 → 下载/注册转化 | 下载或注册人数 / 落地页独立访客 | ≥8% |
| | 下载完成率 | 完成下载 / 点击下载 | ≥85% |
| **Activation 激活** | 激活率 | 30min 内拖入≥1文档且得到带来源正确答 的人数 / 下载人数 | ≥50% |
| | 安装成功率 | 安装成功 / 安装尝试 | ≥90% |
| | Time-to-Value | 下载→首个带来源正确答 中位时长 | ≤30 min |
| **Retention 留存** | 一周留存(W1) | 激活后第 2 周仍有带来源问答 / 激活用户 | ≥40% |
| | 四周留存(W4) | 激活后第 5 周仍活跃 / 激活用户 | ≥25% |
| | 周问答频次 | 人均每周带来源问答次数 | ≥3 |
| **Referral 推荐** | NPS | 标准 0–10「愿意推荐吗」 | ≥30 |
| | 自然推荐比例 | 来自现有用户推荐的新增 / 总新增 | ≥15% |
| **Revenue 收入** | 付费意向率(Beta 免费,用假门/调研测) | 明确表达 Pro/Business 意向 / 活跃用户 | ≥15% |
| | 定价页 → 升级点击 | 点击「升级」/ 看到定价页 | ≥5% |

> Beta 期间全免费,所以 Revenue 用**意向信号**(升级点击 + 调研)代替真实付费,验证 A6。正式收费后替换为真实 MRR / 转化率。

### 5.3 指标护栏(别只看好看的数字)
- **激活率高但留存低** → 首答有用但没有持续价值,查「有用回答命中率」。
- **安装成功率高但激活率低** → 装上了不会用,查 RAG 首答质量与引导文案。
- **北极星涨但点赞率跌** → 用户在用但越来越不满意,提前预警流失。

## 6. 埋点方案(匿名、可关闭、绝不含文档内容)

埋点有双重目的:①运营 §5 的指标;②喂养护城河 AI Deployment Intelligence(见 [docs/06-moat.md](06-moat.md))。

### 6.1 三条铁律
1. **匿名**:只用随机 `anon_id`,不绑真实身份;Free 用户免注册。
2. **可关闭**:设置里一键关闭遥测,默认可见、可撤。
3. **绝不含文档内容**:永远不上传用户文档的任何原文、片段、文件名、问题原文、答案原文。只上传**结构化的元数据**(档位、耗时、成败、原因码、布尔信号)。这条呼应 `frontend/tests` 里「不把自由文本读进内容」的既有安全约束。

### 6.2 事件清单(copy-paste 表)

| 事件名 | 触发时机 | 关键字段(全部为元数据,非内容) | 喂养护城河? |
|--------|---------|-------------------------------|:---:|
| `device_detected` | 硬件检测完成 | `vram_gb` 档位(6/8/12/16/24)、`gpu_model`、`os`(win10/win11)、`ram_gb`、`disk_free_gb` | ✅ 硬件分布 |
| `need_selected` | 用户选/描述需求 | `need_category`(合同/客服/写作/编码/…)、`is_template`(布尔) | ✅ 需求分布 |
| `plan_recommended` | 引擎给出方案 | `model_id`、`quantization`、`backend`、`route`(local/cloud)、`score` | ✅ 推荐输入→输出 |
| `plan_changed` | 用户改掉推荐方案 | `from_model`→`to_model`、`reason_code` | ✅ 方案偏好 |
| `install_step` | 安装每一步开始/结束 | `step_id`、`status`(ok/fail)、`duration_ms` | ✅ 兼容性地图 |
| `install_failed` | 安装失败 | `step_id`、`failure_code`(见下)、`vram_gb`、`gpu_model` | ✅ 失败地图 |
| `install_succeeded` | 安装全部完成 | `total_duration_ms`、`model_id`、`vram_gb` | ✅ 成功地图 |
| `first_qa` | 首次问答返回 | `time_since_install_ms`、`has_citation`(布尔)、`doc_count`、`answer_len_bucket` | ✅ 激活 |
| `answer_rated` | 用户点赞/踩 | `rating`(up/down)、`has_citation`、`model_id`、`need_category` | ✅ 能力边界 |
| `answer_corrected` | Teach My AI 纠正 | `correction_count`、`model_id`、`need_category` | ✅ 能力边界 |
| `rag_indexed` | 文档索引完成 | `doc_count`、`doc_type`(pdf/docx/xlsx/txt)、`chunk_count`、`embed_model`、`duration_ms` | ✅ RAG 效果 |
| `upgrade_clicked` | 点「升级」 | `plan`(pro/business)、`source_page` | 增长 |
| `telemetry_toggled` | 开/关遥测 | `enabled`(布尔) | 合规 |

### 6.3 失败原因码表(`failure_code`)

| 码 | 含义 | 典型处置 |
|----|------|---------|
| `DRIVER_OUTDATED` | NVIDIA 驱动过旧 | 引导升级驱动 |
| `VRAM_INSUFFICIENT` | 显存不够所选模型 | 自动降档 / 转云端手册 |
| `DISK_FULL` | 磁盘空间不足 | 提示清理 / 换盘 |
| `DOWNLOAD_TIMEOUT` | 模型下载超时/中断 | 断点续传 / 换镜像 |
| `BACKEND_INIT_FAIL` | 推理后端启动失败 | 收集日志 → 兼容性名单 |
| `PORT_IN_USE` | 本地端口被占 | 自动换端口 |
| `AV_BLOCKED` | 杀软/防火墙拦截 | 白名单指引 |
| `UNKNOWN` | 未归类 | 必须尽快归因,不允许长期占比高 |

> **护城河用法**:把 `device_detected` + `need_selected` + `plan_recommended` + `install_succeeded`/`answer_rated` 关联起来,就能回答「8GB 显存做英文合同问答,哪个模型装得上且点赞率最高」——这正是 A7 要验证的东西,也是别人拿不到的数据。

### 6.4 埋点最小实现建议
- MVP 阶段可先落**本地日志 + 用户可查看**,再上传聚合。
- 每个事件都过一个 `sanitize()`,白名单字段——**默认拒绝任何自由文本**,从代码层面杜绝文档内容外泄(与 §9 的回归测试挂钩)。

### 7.1 实验纪律(避免自欺)
- **一次一个变量**,否则说不清谁起作用。
- **先定判定规则再看数据**,不许「看到结果再找理由」。
- 样本不够(Beta 早期流量小)时,标为「继续观察」,别急着下结论;必要时用**定性证据**(可用性测试)补足定量的不足。
- 记录**每一个**实验(包括失败的)到实验看板,失败实验也是护城河知识。

## 9. 质量门槛与回归

**目标**:让「不回归」变成自动的,而不是靠人记得。

### 9.1 把 `frontend/tests` 纳入 pre-commit / CI

**pre-commit(本地,提交即挡):** 在 `.git/hooks/pre-commit` 或用 husky/pre-commit 框架:

```bash
#!/usr/bin/env bash
# .git/hooks/pre-commit  —— 提交前跑本地安全测试
set -e
echo "Running frontend/tests before commit..."
bash frontend/tests/run.sh
```

**CI(GitHub Actions 示例):** `.github/workflows/tests.yml`

```yaml
name: tests
on: [push, pull_request]
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - name: Security + unit tests
        run: bash frontend/tests/run.sh   # 退出码非 0 即让 CI 变红
```

> `run.sh` 在没有 Chrome 的 CI 上会自动跳过浏览器 XSS 测试(转义仍由单元测试覆盖);要跑完整套就在 CI 里装 Chromium。

### 9.2 质量门槛(Definition of Done,合并前必须全绿)

| 门槛 | 要求 |
|------|------|
| 安全测试 | `bash frontend/tests/run.sh` 全绿(含 XSS / 危险 API / 无远程资源 / 无硬编码密钥) |
| 埋点净化 | 新增/改动的埋点事件必须只含白名单元数据字段,**无自由文本 / 无文档内容**(加断言) |
| 单元 / 集成 | 触及的模块有对应测试且通过 |
| 无术语回归 | 面向用户的新文案不引入未解释的 AI 术语(评审 checklist) |

### 9.3 里程碑硬件矩阵回归

每个里程碑(新模型、新推荐引擎版本、新安装器)在 §1.2 的矩阵上**回归一遍**:

**回归 checklist(copy-paste):**

```
里程碑:____  日期:____  负责人:____

对每个 VRAM 档位(6/8/12/16/24)× 系统(Win10/Win11):
[ ] 全新环境安装,无人工干预
[ ] 记录安装成功/失败 + 失败原因码
[ ] 记录端到端耗时(目标 ≤30min)
[ ] 拖入标准测试文档,验证首答带来源且正确
[ ] 对比上个里程碑:成功率没有任何一格跌破 90%

放行标准:
[ ] 每格安装成功率 ≥90%
[ ] 无新增失败原因码占比 >5%
[ ] 中位端到端 ≤30min
[ ] 首答带来源正确率不低于上个里程碑
```

> **标准测试文档集**:准备 3–5 份固定的、可公开的测试文档(合同样例、报告、FAQ),每次回归问同一批问题,保证首答质量可纵向对比——这也是把「答得好」纳入回归的关键。
